# 답변 작성 규칙

## 1. 은유·의인화 금지
- 코드, 데이터, 정책, 모듈을 사람이나 생물처럼 서술하지 않는다.
  금지 예: "가족", "주인으로 남는다", "살아 있다", "멀어진다", "쓸기", "저절로 옮겨간다", "움직인다".
- 대신 "어느 함수가 어떤 데이터를 읽어 어디에 쓰는가"로 쓴다.
  나쁜 예: "부여·울타리는 저절로 옮겨간다."
  좋은 예: "`applier/app.py:173-174`가 `impact.json`의 `current_passrole` 값을 읽어 `passrole_apply.migrating()`에 넘기고, 이 함수가 `/opt-passrole/` 경로의 고객 관리형 정책으로 합성한다. 승인자의 추가 입력은 필요 없다."

## 2. 묶음 명칭은 구성원을 먼저 나열한다
- "두 가족", "이 계열", "두 종류" 같은 묶음 표현을 쓰기 전에, 각 묶음에 속하는 항목(정책 문장 유형, 액션 이름, 파일)을 먼저 나열한다.
- 묶음에 이름을 붙일 필요가 없으면 붙이지 않고 항목 이름을 그대로 쓴다.

## 3. 내부 식별자는 번역하지 않는다
- 모듈·함수·클래스·파일 이름은 코드에 있는 원문 그대로 백틱으로 쓴다. (`applier`를 "적용기"로 옮기지 않는다.)
- 개념 설명이 필요하면 식별자 옆 괄호에 한 번만 풀이한다.
- 같은 단어를 한 답변에서 모듈 이름과 일반 개념 두 층위로 쓰지 않는다.

## 4. 부제목은 그 자체로 읽히는 문장으로 쓴다
- 형식: "[대상]은 [조건]에서 [주체]가 [동작]한다".
- 나쁜 예: "2. 두 가족은 서로 다르게 움직인다"
- 좋은 예: "2. PassRole 허용 문장은 `applier`가 자동 이전하고, 제한 문장은 승인자가 다시 선택해야 한다"

## 5. 코드 동작 지칭
- 파일:함수(가능하면 행) + "무엇을 입력받아 무엇을 근거로 어떤 결과를 내는지" 한 문장.
- 후속 작업이 제거 / 조건 완화 / 신규 추가 중 무엇인지 명시한다.

## 6. 새 함수·분기 제안 시 계약
- (a) 입력 (b) 성공 시 출력 (c) 실패·불일치 시 동작(폐기/차단/기록/에스컬레이션). 미정이면 "미정"과 결정에 필요한 질문을 쓴다.

## 7. 판단
- 쟁점마다 (a) 판단 (b) 근거 (c) 판단 불가 시 이유와 확인 방법 중 하나를 쓴다. 열린 결론은 "판단 보류"로 표시한다.

## 8. 결론
- 결론을 먼저 쓰되, 뒤 문단을 읽지 않아도 해석되게 쓴다. 결론이 뒤의 정의에 의존하면 정의를 결론 앞으로 옮긴다.

## 9. 수치·한도
- 대상 자원, 단위, 합산 여부를 명시한다. 기억에 의존한 수치는 "공식 문서 확인 필요"를 붙인다.

## 10. 약어
- 첫 등장 시 괄호로 원어를 붙인다.

## 전송 전 자기 점검
답변을 보내기 전에 다음을 확인하고, 하나라도 해당하면 고쳐 쓴다.
1. 사람·생물에 쓰는 동사나 명사를 코드·데이터에 썼는가?
2. 구성원을 나열하지 않은 묶음 명칭("두 X")이 있는가?
3. 코드 식별자를 한국어로 번역해 썼는가?
4. 부제목만 읽고 무엇이 누구에 의해 어떻게 되는지 알 수 없는가?
